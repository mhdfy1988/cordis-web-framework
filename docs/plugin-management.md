# 动态插件管理：目标、现状与差距

更新日期：2026-10-22。本文保留初始差距研究与后续设计；实时进度只维护在[唯一实施计划](implementation-plan.md)。当前接口与可执行用法以[管理教程](guide/plugin-management.md)及生成签名为准，下文标注“初始”的材料不是当前功能缺失清单。

## 目标与当前结论

宿主运行后，能够安装一个原先不在宿主构建中的独立插件包，再启动、停用、重新启动及卸载；不要求修改宿主源码、重新构建或重启宿主。插件自身允许独立编译构建，不能把“宿主构建时已经包含、点击后才加载”当成全新插件安装。

安装记录、用户启停意愿和配置需要持久保存，刷新或重启后恢复；实际运行状态重新计算，不把上次的 ready 快照当成本次就绪。

P0 时交付仅为可信模块装配与生命周期底座；当时文档应用的目录管理页及 localStorage 不代表框架能力。后续已增加框架管理子系统、平台存储／加载、无界面装卸闭环和宿主动态资源，并将文档管理页迁移为统一接口的呈现。W1—W9 原测试保留历史范围，动态管理依据 P 阶段新证据，不倒写为旧阶段已完成。

### 已确认的职责归属

插件安装、启用、停用、卸载、配置保存与重启恢复是框架自身的基础能力。插件管理页面只是其中一种呈现形式；程序接口、页面和命令行入口必须调用同一套框架管理契约，不各自实现管理规则。没有管理页面或其他可选呈现插件时，框架仍须能完成完整管理闭环。

下文“管理层”均指框架内的插件管理子系统，不是要求应用另写管理器，也不是必须安装一个可选业务插件才能获得基础管理。平台存储、代码加载等实现通过适配边界接入；核心拥有规则和协调责任，不代表把所有平台代码放入同一个核心文件。页面与命令行如何呈现可以独立选择，不改变能力归属。

## 统一术语与状态所有权

| 术语 | 含义与所有者 |
| --- | --- |
| 安装 | 获取、校验、保存独立插件包并登记版本；不等于执行插件代码。未来由插件管理层及平台存储适配负责 |
| 启用意愿 | 用户希望插件运行的持久配置；不保证当前依赖满足。未来由管理层保存 |
| 启动／停用 | 创建或释放插件运行实例；由管理层协调现有运行时，不直接等同安装／卸载 |
| 卸载 | 在依赖策略和清理条件满足后移除安装登记及包资源；插件用户数据是否保留须另有明确策略 |
| 实际运行状态 | 等待依赖、启动中、就绪、失败、停止中、已停止或清理失败；由运行时观察，不直接持久恢复 |
| 管理操作状态 | 安装中、卸载中、失败及中断恢复信息；与安装记录、启用意愿、运行状态分别表达，具体协议尚待设计 |

同一插件可以“已安装、用户已启用、实际等待依赖”；也可以“已安装、用户已停用、无运行实例”。这些情况不能压成一个布尔状态。删除包不等于删除业务数据，停止应用也不自动清空安装记录。

## 初始能力与缺口（P0 快照）

| 领域 | 已有基础 | 尚缺的框架能力 |
| --- | --- | --- |
| 独立交付 | 插件身份、实现版本、API 范围、服务版本、配置校验 | 独立插件包清单与入口、资源布局、依赖交付和构建模板；共享 Vue／框架契约的解析规则 |
| 获取与安装 | 可信模块目录 | 包来源、校验、暂存、正式登记、失败恢复及平台存储；不能仅把 URL 传给 import 就称为安装器 |
| 模块解析 | 接收已经可用的插件定义 | 从安装记录找到并动态导入独立代码，区分浏览器与 Node 的加载、资源地址和依赖解析 |
| 增量装配 | 全量版本、配置、绑定与依赖图预检；运行时允许继续 load | 在存活运行时中验证变更、处理冲突及影响范围；失败不应无差别关闭宿主 |
| 持久恢复 | 通用配置合并、来源追踪和校验 | 安装目录、版本、启停意愿、插件配置的读写与启动恢复；明确存储隔离、格式升级及写失败行为 |
| 停用与卸载 | 依赖生命周期、取消信号、逆序清理、清理错误诊断 | 依赖者的拒绝／联动策略、卸载前清理门禁、包与共享资源回收、用户数据保留策略 |
| 动态界面／接口 | 可撤销的界面、命令与导航；Vue 组件目录；Node HTTP 宿主 | 运行中组件和样式资源登记／撤销、接口与静态资源动态接入，并统一归属插件生命周期 |
| 长期管理 | 运行实例与诊断快照 | 同插件并发操作协调、操作记录与中断恢复、历史记录保留及引用释放策略、统一管理接口 |

已有版本校验和服务调度应复用，不另造第二套依赖引擎；“动态安装”不等于同时承诺任意版本的无损热升级。升级、回退、远程市场和不可信插件沙箱需要独立定义，不作为隐含保证。

## 管理流程与不变式

第 1 轮：宿主启动时没有插件 A。输入 A 的独立包来源，经校验、暂存和登记，输出安装记录；默认不因安装自动执行。具体包格式和来源协议待定。

第 2 轮：用户启用 A。管理层校验配置、版本和服务依赖，导入入口并交运行时激活；输出真实运行状态。缺依赖、导入失败和激活失败分别报告，不能把“已启用”显示为“已就绪”。模块顶层代码可能在导入时执行，运行作用域不是安全隔离。

第 3 轮：用户停用 A。按明确的依赖策略处理消费者，等待真实清理，撤销界面、命令、订阅等贡献；持久保存停用意愿。刷新或重启后仍保留安装记录，但不自动启动 A。

第 4 轮：用户重新启用，再卸载 A。卸载先检查依赖及停止结果；清理失败时保留故障与可恢复记录，不报告成功。成功移除安装记录及可删除的包资源，按明确策略保留或删除用户数据；重启后不再加载 A。

关键不变式：

- 管理操作必须有一致的配置来源；持久化失败不能被静默当成已保存。
- 同一插件的冲突操作必须协调；发生中断后能判断哪些步骤已完成，而非只改界面开关。
- 无关插件与宿主继续运行；依赖者的变化必须可解释，不按加载顺序偷偷选择提供者。
- 清理超时不等于清理完成；不配合的同进程插件不能靠普通取消信号保证强制终止。
- 卸载业务贡献不等于 JavaScript 引擎立即卸载模块代码；不能用不断追加随机 URL 作为无限热重载方案。

## 平台边界与后续设计方向

共用管理契约和状态语义，浏览器与 Node 分别提供包存储、解析和加载适配。纯静态站点可以运行浏览器插件，但不能据此宣称具有服务器包安装或后台进程管理能力；浏览器安装后的持久存储、资源寻址和跨来源限制需实际验证。

管理能力由框架插件管理子系统统一提供，平台适配实现存储、代码加载和资源接入；页面不是这些规则的所有者，也不作为管理能力的启动前提。引导管理与恢复入口如何避免被自身停用，需要先定义。第一轮优先跑通可信独立包的完整闭环；具体格式、来源、持久化介质与是否接入上游加载器尚未选定，不在本文虚构公共 API。

## 修改范围与影响（设计及实施核对依据）

这是一轮框架能力扩展，伴随局部架构调整，不是纯保行为重构，也不是只在管理页新增按钮。以下记录设计落点；已落地公开入口、限制及使用方式见管理教程，不用设计表替代当前 API 参考。

### 修改落点

| 位置 | 建议修改 | 对现有调用方的影响 |
| --- | --- | --- |
| 插件契约 `src/contracts` | 在运行定义之外增加独立包清单、安装记录、管理操作和状态投影；不把安装状态混入现有运行状态 | 尽量保留 setup、服务声明和作用域契约；独立交付插件须遵守新增包规范，兼容范围需明确 |
| 新增框架插件管理子系统 | 协调安装／启停／卸载、并发操作、失败恢复和持久记录，作为程序接口、管理界面与命令入口共用的规则所有者 | 无页面时仍可使用全部管理能力；应用不再自己复制管理规则，管理子系统不拥有业务草稿或用户数据模型 |
| 装配模块 `src/plugin-composition` | 保留启动时全量预检，增加面向存活运行时的增量变更校验与协调 | 不能直接复用全量装配失败时关闭新运行时的策略来处理增量失败；应说明影响哪些插件并保留无关能力 |
| 宿主契约与 `src/hosts/shared/lifecycle.ts` | 接入受控管理协调者；启动时恢复，关闭时拒绝新管理操作并等待在途操作收尾 | 两种宿主的启动／关闭顺序需补回归；不为方便管理而向所有页面暴露原始运行时或平台私有对象 |
| 配置与持久化适配 | 复用来源解析和校验；新增安装记录、启停意愿、插件配置与操作记录的读写边界 | 明确应用／实例隔离、存储格式升级、写入失败和中断恢复；运行快照不直接作为持久真值 |
| Cordis 运行适配 `src/runtime-cordis` | 复用 load／stop、依赖与清理机制；评审长期记录保留、已停实例引用释放和依赖联动 | 不能为释放引用破坏已有诊断契约；历史归档与当前实例投影分开，反复启停后仍能正确追踪故障 |
| Vue 呈现及 Node HTTP 适配 | 提供生命周期受控的组件、样式、接口与资源登记／撤销；按平台选择实现 | 保留现有界面组合契约；需验证卸载当前页面、路由冲突、在途请求和样式释放，不只验证 setup 成功 |
| 构建与交付工具 | 增加独立插件构建模板、入口与资源产物验证，收口共享框架／Vue 依赖解析 | 插件可独立构建，宿主无须重建；防止重复运行库、共享契约身份不一致或不兼容版本混用 |
| 管理页与验收 | 页面只调用管理契约并展示状态；增加宿主启动后才提供全新包的黑盒验收 | 文档站私有目录管理与设置保存须迁移；原先预注册插件启停证据不覆盖动态安装 |

### 保留的能力与兼容责任

- 继续复用插件 setup、服务消费／提供、取消信号与资源清理方式；不无故重写业务算法、编辑状态或数据模型。
- 界面位置、命令、导航、主题及浏览器／Node 分端运行的方向保留；新增加载和管理机制通过这些边界接入。
- 保留现有静态装配入口，作为明确支持的内置插件模式，与动态管理模式区分；不能在动态管理失败后静默回到旧装配链路。
- 独立包规范和新的管理契约可能带来适配成本。若确需改变现有公开语义，先明确破坏性变化、版本与迁移说明，不能因当前为 0.0.0 就默认消费者无需兼容。
- 当前文档消费应用的 localStorage 设置和可信目录不能直接宣称已变成框架配置。迁移须明确旧键、配置版本、插件身份映射、导入时机和失败处理；不静默重置用户选择、不维护两份相互覆盖的启停真值。具体迁移规则尚待设计，本轮不修改消费工程。

### 主要风险与验证影响

| 风险 | 必须保持的约束 | 需要补充的证据 |
| --- | --- | --- |
| 依赖联动 | 提供者停用／卸载的影响明确，消费者恢复不依赖偶然顺序 | 缺依赖、联动停用、恢复、版本冲突及清理失败用例 |
| 动态资源撤销 | 插件退出后资源按责任释放；在途业务按契约处理 | 实际组件／样式／路由／监听撤销、HTTP 在途排空及重复启停 |
| 执行与保存不一致 | 启动成功但保存失败必须同时表达，不能报告整体成功；补偿也可能失败 | 存储写失败、操作中断、恢复及重复操作用例，不宣称跨存储和运行时天然原子 |
| 新代码执行入口 | 兼容校验、来源信任与安全隔离分别判断；不把 manifest 能力声明当权限沙箱 | 坏包、路径／资源校验、导入失败和信任边界检查；不可信隔离另立验收 |
| 宿主就绪判断 | 可选插件主动停用不拖垮宿主，必需能力失败仍影响就绪 | 管理后的必需范围、audit、宿主状态与 HTTP 就绪探针一致性 |
| 长期运行 | 不靠无限历史引用或随机模块 URL 支撑反复装卸；清理失败不算已释放 | 反复启停的资源／引用保留核对，区分功能撤销与引擎模块缓存 |

现有 W1—W9 证据仍是历史事实。实现上述修改后，须根据受影响源码、公开导出、构建、宿主和使用说明重新生成候选并补验，不能继续引用旧冻结 kit 或旧完整性结果作为新框架通过的证明。独立包验证、浏览器／HTTP 真实运行和应用配置迁移分别验收；文档检查通过不代表这些行为已通过。

### 职责组织与推进顺序

框架管理子系统接收包来源、配置和用户操作，输出安装记录、操作结果与状态；平台适配提供存储、解析、代码与资源接入；运行时负责激活、依赖与清理；可选管理页面只表达意图和展示结果。引导管理及恢复入口不能依赖随意可停的产品布局，其生命周期策略仍须收口。

1. 先确定包规范、管理契约、状态所有权及信任边界，同时评估上游机制复用，不先改页面。
2. 建立管理协调与持久化／加载适配，在存活运行时接通增量装配；选择能揭示风险的最小可信独立包验证。
3. 调整宿主启动恢复、关闭排空、就绪判断与长期清理，完善动态界面和服务资源撤销。
4. 将现有文档应用的私有设置与管理规则迁移到统一能力，验证原有阅读与业务交互保持。
5. 最后完成本文件的全新包、两种平台适用路径、故障和重启恢复验收，再评估交付；远程市场、自动升级和不可信插件隔离不混入第一轮完成口径。

用户已授权 P1—P8 实施并逐阶段检查；JSON／ESM 包、Zod、现有 Cordis、Node 文件与浏览器 IndexedDB 适配的实际取舍见[包规范](plugin-package.md)。授权不含公开发布或部署，远程市场、任意来源和不可信沙箱不在首版范围。

### 阶段交付与门槛

实时复选框只维护在实施计划；下表解释对应阶段的输入、交付和退出条件，不另建进度清单。按 P1 至 P8 推进，先框架程序接口、后呈现入口；不能以管理页先做出来代替底层完成。

| 阶段 | 输入与交付 | 退出条件 |
| --- | --- | --- |
| P1 规范与复用决策 | 基于现有契约，确定独立包身份、双平台入口、资源／共享依赖规则、可信来源边界；评估上游加载器与固定 Cordis 基线，保留固定源码证据和选型取舍 | 有合法／非法包示例与兼容策略；明确复用哪些实现、不复用哪些；不靠临时改依赖或宿主重构建完成导入 |
| P2 管理契约与状态规则 | 定义框架统一管理接口、四类状态、错误、操作冲突与提交顺序，确定静态内置插件和动态插件的管理边界 | 无页面的契约用例可表达安装与启用分离、启用但等待依赖、停用持久保存、清理失败禁止成功卸载；明确跨插件依赖图变更的协调，不能只锁同名插件 |
| P3 存储、加载与恢复基础 | 实现平台包存储／校验／解析适配、版本化安装记录和操作记录，支持故障注入；确定配置迁移规则 | 获取失败、坏包、写失败和中断有明确结果；刷新／重启可恢复安装记录与启停意愿；执行代码前后的信任边界清楚 |
| P4 无界面管理闭环 | 通过公开框架接口接通安装、增量预检、启用、停用、再启用和卸载，复用 Cordis 调度 | 宿主启动后接收未知独立包，全程不改宿主构建、不重启；不含管理页面也可完成闭环；失败影响范围可解释 |
| P5 宿主与动态资源集成 | 接入启动恢复、管理操作排空、必需能力就绪、记录保留，以及 Vue 组件／样式和 HTTP／静态资源生命周期 | 浏览器与 Node 的适用路径均有真实运行证据；当前页面卸载、在途请求、反复启停、双实例和清理失败不破坏宿主与无关能力 |

## 验收标准

1. 先启动宿主并固定其构建产物，再提供此前未包含的独立插件包；整个装卸过程不改宿主源码、不重建或重启宿主。
2. 安装与启用分开验证；启用后出现真实服务、命令或界面，不以安装登记代替运行。
3. 停用后贡献与登记的资源释放，无关插件可继续使用；再启用创建有效实例，不误读历史状态。
4. 刷新／重启后保持安装版本、配置和启停意愿；缺依赖与启动失败仍如实显示。
5. 卸载后重启不再加载；用户数据按已声明策略处理。
6. 覆盖坏包、版本冲突、缺依赖、导入／激活失败、存储失败、并发操作、清理失败与安装中断；不得静默回退旧链路。
7. 浏览器与 Node 各自留下适用平台的真实证据；前端插件界面和后端服务资源分别验证，不将任一平台通过泛化为全平台完成。

P4—P7 已有无界面、Node 文件回读、真实 HTTP／资源、Chrome 事后未知包安装、动态组件／样式、刷新恢复与卸载、原生对象 URL 释放及故障回归证据；命令见管理教程，输出在 output/management。P8 工程外同包交付结果由唯一计划及 output/package-check-result.json 记录，不提前标记通过。旧样例构建、预注册启停或 localStorage 不替代这些检查。
