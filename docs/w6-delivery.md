# W6 本地交付、模板与发布边界

## 范围与版本

框架仍使用中性工程名 `cordis-web-framework`，包版本 `0.0.0`、`private: true`、`UNLICENSED`。这是开发候选，不是正式 npm 版本，不能因为可以 `npm pack` 就宣称公开可用。正式名称、许可证、远端仓库和部署目标由项目负责人决定，本阶段工具不登录、不上传、不初始化 Git。

2026-10-22 用户确认本轮只完成本地交付准备，暂不公开发布或部署。因此 W6 的退出条件为本地候选、模板、门禁和文档通过；目标渠道验收留待后续明确授权，不是被本地测试替代。

框架包、插件实现、插件 API、服务契约和业务数据分别版本化。当前插件 API 为 `1.0.0`、装配格式为 `1`；这些不是框架包版本。当前未承诺任意 0.x 升级兼容，也没有历史正式发布可做真实 N−1 升级验收。

正式版本采用语义化版本：兼容修复更新修订号，兼容新增更新次版本，不兼容公开 API 更新主版本；0.x 阶段破坏性调整需明确迁移与版本说明，不靠“未到 1.0”隐藏风险。已发布内容不可原地覆盖。

## 命令与证据链

在项目根目录使用锁定的 Node 24、npm 11.9.0：

```powershell
npm.cmd ci --no-audit --no-fund
npm.cmd run check:metadata
npm.cmd run test:delivery
npm.cmd run verify:delivery
npm.cmd run check:release
```

- `check:metadata`：核对包／锁、公开入口、运行依赖组合、插件 API 和 CHANGELOG 格式，不构建或访问远端。
- `test:delivery`：先执行 `test`，再执行已有 `test:package`，之后从同一 tarball 导出三种模板；将整套候选搬到新的工程外目录，分别安装并 `ci`、构建、真实运行，全部成功才写入 `output/delivery-result.json`。
- `verify:delivery`：离线重算输入与候选文件摘要；缺失、修改、额外文件、包不符或路径越界时失败。不重新跑行为，也不证明未经测试的平台兼容。
- `check:release`：正式发布前置检查，当前**应失败**，列出 private、许可证、正式版本、仓库、版本日志等缺口。即使未来通过，也只代表本地前置条件，不会执行发布或保证渠道可获取。

完整性使用 Node 内置 SHA-256／SHA-512，版本解析复用现有 semver；无需新依赖。候选文件及各模板的锁记录同一个 tarball 完整性。框架内部 Cordis 补丁仍由原构建守卫验证并内置，消费方不运行 postinstall。

输入摘要覆盖源码、脚本、测试、样例、模板、构建配置、依赖锁、补丁、兼容基线、使用文档和更新日志。`docs/implementation-plan.md` 是唯一实时任务指针，不参与摘要；否则回写阶段状态会制造无意义失效。`output`、`dist` 和 `node_modules` 不作源码输入；交付包本身及整个导出目录另算摘要。没有 Git 时使用内容身份，不伪造提交来源或供应链签名。

失败只终止当前候选，不回退旧实现或覆盖旧成功证据。旧指针仍可能存在；使用前必须执行 `verify:delivery`，不能只看文件存在或时间。目录中的 `evidence.json` 和 `delivery-result.json` 是本地验收证据，不是加密签名或防恶意篡改证明。

## 三种可搬移模板

候选目录 `output/delivery/<唯一标识>/kit` 包含 `framework.tgz`、文档、第三方声明和 `templates`。模板代码来自现有样例及少量启动接线，不维护第二套图片或记录业务，也不复制框架 `src`。三个模板各自独立安装，依赖路径均为 `file:../../framework.tgz`。

| 模板 | 来源与运行 | 产物／限制 |
| --- | --- | --- |
| browser | PNG 样例；安装后 `npm.cmd run build` | `web` 的四个文件放在 HTTP(S) 静态目录；相对路径，可放子路径，无后台 API；不承诺 file:// 或离线启动 |
| node | 最小公共插件＋Node HTTP 宿主；安装后 `npm.cmd start` | 日志中的随机回环地址，`/health/ready`；无数据库和登录 |
| fullstack | 记录编辑样例；安装、build、start | 同源页面／JSON API、`data/records.sqlite`；实验性 SQLite、本机身份夹具，不可直接公网部署 |

交付模板包含本候选实际安装并验收的锁文件，使用 `npm.cmd ci --ignore-scripts --no-audit --no-fund`。生成阶段在隔离目录先 install 产生锁，再 ci 和运行，成功后将锁收入候选。模板显式依赖 Vue／Zod，浏览器构建显式选择 esbuild；框架单包仍会安装 Node 宿主依赖，但纯浏览器构建不包含服务器代码。未为减少安装量仓促拆包。

验收模板时，浏览器模板使用自身安装的 esbuild 生成压缩生产资源，复用 W5 实际 Worker／PNG 下载回读和资源释放黑盒。服务端模板请求就绪并停止；全栈模板用真实 Chrome 保存，直接查询独立 SQLite 确认结果并停止。验收用临时目录、随机回环端口和独立 Chrome，不替换用户主入口。

## 部署安排与边界

静态部署只上传 browser 的 `web` 文件，保留文件名、层级和 JavaScript MIME。Worker 必须同源可取，启用 HTTP(S)，不要注入服务器密钥；建议设置 W5 静态验证采用的 CSP 与 nosniff。真实托管验收应重新执行导入→缩放→下载解码，并核对 Worker 资源路径、错误和取消，HTTP 200 不足以证明部署成功。

服务端部署要另行确定正式认证、生产存储、配置／密钥来源、反向代理、TLS、健康探针和退出预算。当前全栈样例的身份夹具**不是生产方案**，不为了完成 W6 直接暴露公网。

本地静态子路径和三个模板真实运行不等于已部署 GitHub Pages、服务器或 npm。按用户决定，本轮收口本地准备部分，目标部署明确不在本轮执行范围内，仍未执行。

## 升级门禁

`compatibility/baseline.json` 固定当前公开入口、插件 API、默认运行／peer 依赖、Node 范围和 Cordis 基线，检测未评审漂移。它不是自动 API 差异分析器：函数签名与行为还依赖严格类型消费、契约测试和两种应用的真实运行。

升级步骤：

1. 核对现有公开接口及来源，判断是兼容新增还是破坏性变更；记录受影响的插件、应用与数据。
2. 对 Cordis 升级核对上游 PR #133 是否已包含，重新评审补丁并更新守卫，禁止继续误套或静默回退。
3. 在独立分支／副本调整依赖、锁、适配与迁移说明；明确评审后再改基线，不写“自动接受新版本”脚本。
4. 重跑 `test:delivery`：原契约、严格工程外类型、Node／浏览器／布局、全栈／纯浏览器以及模板都消费新候选。
5. 将来有历史正式版本后，增加 N−1 已发布包及真实持久数据的升级／恢复测试。目前不能用“新装 0.0.0 成功”冒充这一项。
6. 已发布版本日志、包清单、锁、标签和渠道一致后才发布；版本段填写真实发布日期。部署目标实际获取、运行及正式安装分别记录。

检查器自测覆盖合法本地候选与正式版本夹具、错误锁／入口／插件 API／日志、产物篡改、额外文件和路径逃逸；真实 `check:release` 接线确认失败会传递而不输出成功。测试夹具的 MIT、仓库和版本是隔离测试数据，不是项目授权。

## 本轮验收记录

2026-10-22，本地 `check:metadata`、`test:delivery` 与 `verify:delivery` 已通过。Node 契约／边界回归为 134 项；工程外同候选包保留 W2／W3／W4／W5 流程，三个导出模板再分别安装、ci 和实际运行。Chrome 155 的模板黑盒下载 PNG 从 320×180 缩放到 160×90，实色及透明通道正确，Worker／对象 URL 清理通过；全栈模板直接查询 SQLite 确认保存，服务端模板请求就绪后真实停止。压缩后的桌面悬停与窄屏截图已检查，样例界面没有改版。

正式 `check:release` 已实跑，按预期非零退出，未把 private／未定许可证／0.0.0 放行。没有联网刷新安全审计，W5 的生产 0／开发 4 条高危只是此前记录，不作为本轮新安全结论。当前没有实际远端发布、目标托管验收或历史版本升级证据。候选的准确 SHA、工具链、独立安装目录与报告在 `output/delivery-result.json`，无需手抄临时路径作为固定使用入口。

可复用经验：先让同一包通过原有消费验证，再将模板整体搬出工程、安装自身构建工具和验收锁文件；完成后固定输入／产物身份。这样不会因本仓的开发依赖或旧报告掩盖交付缺口。本地门禁与正式发布前置门禁保持两种状态；文档改变也会使旧候选失效，本轮在最终文档同步后重新完整验收。
