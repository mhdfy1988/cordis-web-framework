# Cordis 基座的 Web 通用框架规划

日期：2026-10-22。状态：W0 定位、W1 核心、W2 宿主、W3 全栈闭环、W4 界面组合及 W5 跨应用样例已完成，见 [W1](w1-core.md)、[W2](w2-hosts.md)、[W3](w3-fullstack.md)、[W4](w4-ui.md)、[W5](w5-browser-tool.md) 记录。独立工程名为 cordis-web-framework；采用 Fastify／可选 Vue 与 Vue Router、严格 JSON 通信及独立 SQLite 样例；纯浏览器图片样例不改变核心业务边界。正式认证、品牌和发布渠道仍待后续选择，不自动提交或发布。

## 1. 定位与文档关系

动态插件管理由框架统一提供，不是应用管理页功能。P 阶段已实现可信 JSON／ESM 包安装、启停、卸载、持久恢复及平台资源接入；当前限制与用法见[教程](guide/plugin-management.md)，交付验收状态只见实施计划。初期“插件市场、任意 URL 安装非目标”保留为历史与信任边界；受控可信包不等于任意 npm 安装或不可信沙箱。

面向当前使用的说明已从研发记录中独立整理，入口为[开发者手册](guide/index.md)与[API 参考](reference/index.md)，历史阶段集中在[研发记录](records.md)。W7 内容核对不代表 W8 文档站或 W9 独立开发验收已完成。

W6 接续：本地交付、三个应用模板与版本／兼容／候选完整性门禁见 [W6 说明](w6-delivery.md)。用户确认本轮只完成本地交付准备，暂不公开发布或部署；W6 本地范围与整体规划中的正式渠道验收分开，不将后者计为完成。

目标：提供一套以 Cordis 为运行基础、可组合和可替换的 Web 应用框架。共用核心，浏览器与服务端分别适配、独立运行；具体项目主要编写业务插件与装配配置，不复制框架源码后各自修改。

已明确的方向：

- 聚焦 Web 通用框架，既考虑纯浏览器，也考虑服务端和全栈应用。
- 一套公共核心、两种宿主，不开发两套相互独立的框架。
- 采用“一切皆插件”的组合理念，默认界面与基础能力实现可替换。
- 先完整规划，再确认边界、技术组合与第一版范围；不因单项能力被提及就立即实施。
- 桌面适配、分布式治理暂不展开。

已确认：通用框架独立建立于 cordis-web-framework 仓库，采用中性工程名；FluidBlock 保留为后续消费应用，不改名、不删除。正式品牌名称以后单独确认。

本文负责整体能力地图与架构背景，[实施计划](implementation-plan.md)是本项目唯一执行指针。[W0 架构基线](architecture-baseline.md)规定首版范围、职责和状态所有权；[复用证据](reuse-evidence.md)规定来源、缺口与转移验证。原 FluidBlock 中的规划保留为来源快照，不维护本项目的实时进度。

## 2. 应用范围与非目标

| 应用形态 | 装配方式 | 交付形态 |
| --- | --- | --- |
| 纯浏览器应用 | 公共核心＋浏览器宿主＋前端／本地处理插件 | 静态资源，可独立部署，无须后端 |
| 服务端应用 | 公共核心＋服务端宿主＋接口／业务／任务插件 | 可独立启动的服务，不依赖前端组件 |
| 全栈应用 | 两种宿主＋通信契约＋各端插件 | 前后端可同源或分离部署，各自拥有运行状态 |

初期面向工具、编辑器和管理系统等交互式 Web 应用。不承诺所有 Web 场景均已覆盖。

当前非目标：

- 桌面与移动原生宿主。
- 微服务注册发现、网关集群、分布式事务及跨服务调度平台。
- 插件市场、任意 URL 安装和任意第三方代码的安全沙箱。
- 自研 HTTP 引擎、数据库驱动、身份协议或通用组件编译器。
- 将图片、序列帧、动作编排等具体业务协议塞入框架核心。
- 为所有业务统一数据库表、审批流程、角色模型、撤销栈或全局可写状态。

服务端渲染（SSR）、搜索引擎优化、离线同步、多租户和多人协作列为需求触发的后续扩展，不预先承诺支持，也不阻止未来通过独立边界接入。

## 3. 架构与依赖方向

```text
具体应用：业务插件、产品界面、应用配置、装配方案
                    │
       可选基础插件与能力组合包（Starter）
        界面、HTTP、安全、数据、文件、任务……
                    │
       浏览器宿主              服务端宿主
       DOM／浏览器能力         HTTP／系统能力
            └──── 明确的网络契约 ────┘
                    │
                公共核心
     公共契约、装配、配置、生命周期、诊断
                    │
                Cordis 适配
                    │
                  Cordis
```

图表示职责关系，不要求立即创建全部目录或占位包。浏览器和服务端是两个独立运行实例，不共享内存容器；共享的是可移植契约、纯逻辑与框架实现。

| 部分 | 拥有 | 不拥有 |
| --- | --- | --- |
| 公共契约 | 插件、服务、配置、错误、版本、资源与宿主能力约定 | Cordis 私有类型、DOM、数据库连接、具体业务 |
| 公共核心 | 装配规则、实例边界、基础诊断与配置协调 | 产品菜单、业务算法、第二套依赖调度引擎 |
| Cordis 适配 | 既有生命周期／依赖行为的接入和状态映射 | 独立复制 Cordis 调度；用库升级悄悄改变公开语义 |
| 宿主 | 环境接入、启动与退出、可用能力、入口配置 | 跨插件业务流程和万能可写应用状态 |
| 基础插件 | 一项完整公共能力及其资源清理 | 其他插件私有数据、产品业务规则 |
| 业务插件 | 业务状态、规则、工作台与业务数据格式 | 对框架私有实现的依赖、跨区操作其他插件 DOM |
| 能力组合包 | 经过验证的一组插件、依赖、默认配置和覆盖入口 | 隐藏的提供者竞争、无法关闭的默认业务 |

通用工程能力优先评估成熟库，通过必要适配接入；框架掌握组合规则和公开语义，不为隔离增加无实际价值的转发层。现有能力应先检索、复用，再评估新实现。

## 4. 完整能力地图

下面是框架生态需要考虑的能力，不等于全部属于核心依赖或全部进入第一版。

### 4.1 公共核心

| 能力 | 规划内容与边界 |
| --- | --- |
| 插件契约 | 身份、入口、配置校验、实现／API／服务版本、宿主要求；扩展元数据须有明确规则 |
| 装配预检 | 可信模块目录、显式绑定、重复标识、冲突、兼容和依赖环；拒绝无效方案，不先部分激活 |
| 生命周期 | 启动、等待、激活、就绪、停用、失败与清理；等待完成不等于就绪 |
| 资源作用域 | 监听、订阅、定时器、资源句柄与后台活动的归属和释放；保留清理失败证据 |
| 受控退出 | 停止接单、取消或排空、释放依赖；超时不冒充实际资源已释放 |
| 配置 | 默认／文件／环境／显式覆盖的确定优先级、校验及来源诊断；密钥不进入浏览器配置 |
| 状态与诊断 | 唯一运行状态、只读检查、故障定位及订阅；不从日志反推状态 |
| 日志契约 | 结构化日志、上下文、级别与最小错误输出；具体输出器可替换 |
| 宿主能力契约 | 声明运行目标和所需能力；不兼容环境在激活前明确拒绝 |

### 4.2 浏览器基础

| 能力 | 规划内容与边界 |
| --- | --- |
| Vue 呈现 | 组件解析、挂载、卸载、错误处理与状态投影；Vue 不进入运行时核心 |
| 界面扩展 | 根贡献、位置声明、候选选择、作用域、等待、撤销和冲突诊断；既定语义的本仓实现与限制见 [W4](w4-ui.md) |
| 页面路由 | URL、参数、深链接、刷新恢复、未找到和路由冲突；路由与菜单不是同一真值 |
| 布局与导航 | 默认布局、导航和工作区作为可替换插件；不固定产品页面 |
| 命令与快捷键 | 操作注册、可用状态、执行和清理；菜单／按钮／快捷键复用同一操作路径 |
| 状态组织 | 应用、页面／编辑实例、服务端数据缓存分清所有者；不提供任意修改全部业务对象的万能容器 |
| 设计基础 | 主题、设计变量、基础控件、国际化、键盘、焦点和可访问性约定 |
| 浏览器能力 | 文件选择、下载、本地存储、Worker、对象 URL 和监听等资源接入 |

界面扩展协议、控件实现和业务工作台分开。扩展位置不能成为无限堆控件的理由；默认页面仍需明确主任务、信息层级、密度和受限视口验收。具体产品的视觉风格不由核心冻结。

### 4.3 服务端基础

| 能力 | 规划内容与边界 |
| --- | --- |
| HTTP 接入 | 服务启动、路由、中间件、静态资源、请求体与连接限制；业务插件不自行启动重复服务器 |
| 请求处理 | 参数校验、请求上下文、错误映射、超时和取消；请求身份不能放入插件全局单例 |
| 身份与权限 | 成熟认证／会话接入、授权检查与身份传递；业务决定资源权限，前端隐藏按钮不代替服务端授权 |
| 数据访问 | 数据源、连接、事务、迁移和关闭；业务拥有表结构、事务边界及数据保留规则 |
| 文件／对象存储 | 上传、下载、访问控制、路径与容量限制；框架不定义产品工程文件语义 |
| 后台任务 | 排队、进度、并发、取消、结果查询；明确内存任务还是持久任务及崩溃后行为 |
| 实时通信 | SSE／WebSocket 的连接、订阅权限、断线与恢复；不默认承诺不丢消息或恰好一次 |
| 定时与缓存 | 按需接入调度、缓存及失效；不把缓存视为权威业务数据 |

连接池等实例资源与请求内事务、任务实例必须分别管理。默认单进程模块化应用，不因为使用插件就拆成微服务。

### 4.4 前后端通信

必须一起定义：

- 请求、响应、错误、接口版本及运行时校验；共享 TypeScript 类型不能替代网络输入校验。
- 日期、二进制、分页、上传和流式内容的表达；不强制所有内容塞进统一 JSON 外壳。
- 身份凭据与服务端权限检查；不得信任客户端自报用户身份或追踪字段。
- 请求／任务关联、超时、取消、重试和断线规则；有副作用的调用不默认自动重试。
- 浏览器取消等待与服务端实际取消分别表达；已提交数据不会因客户端取消而自动回滚。
- 前后端版本不同时的兼容窗口、错误提示与升级策略。
- 进程内服务契约与网络接口分别设计，不能把容器对象或服务实例直接序列化跨端。

网络客户端、接口描述与必要生成工具属于适配能力；是否代码生成、是否采用 OpenAPI，在技术选型阶段确认，不先自制 RPC 协议。

### 4.5 日志、可观测性与安全

| 能力 | 规划重点 |
| --- | --- |
| 日志 | 统一接口、结构化字段、实例／插件／请求／任务上下文、脱敏、级别、输出故障及容量控制 |
| 输出适配 | 浏览器控制台、有界缓存／可选上报；服务端结构化标准输出，按部署需要接文件或日志平台 |
| 诊断 | 当前插件与依赖状态、激活／清理异常；不建立第二份可写运行真值 |
| 健康与就绪 | 区分进程存活与必需能力已就绪；无效装配或未就绪时不接业务流量 |
| 指标与追踪 | 请求耗时、错误率、任务积压、资源占用及跨端关联；采集粒度、采样和成本受控 |
| 审计 | 敏感操作主体、对象、结果与时间，独立访问／保留规则；不是普通调试日志 |
| 安全基线 | 服务端授权、密钥隔离、输入／上传限制、跨域与会话策略、管理入口保护 |
| 容量治理 | 并发、队列、日志缓存、文件大小、执行时间和资源限额；不能无限积压 |

日志输出器未启动或失效时保留最小错误输出，避免日志依赖环。日志中不默认记录令牌、完整请求体或用户素材；上报需有明确策略。

首版信任边界候选是随应用构建发布的可信插件。能力声明不是恶意代码沙箱；运行隔离与安全隔离分开，不以两实例互不干扰宣称第三方代码安全。生命周期可停用也不意味着能强杀任意同线程代码。

### 4.6 开发与交付体系

| 能力 | 应提供的产物 |
| --- | --- |
| 插件开发支持 | 公共接口、最小插件、错误处理、资源清理、能力替换及调试示例 |
| 应用模板 | 纯浏览器、服务端、全栈模板；框架作为依赖使用，不复制内部源码 |
| 构建边界 | 浏览器／服务端产物分离、包导出、资源地址、基础路径与依赖隔离；密钥和 Node 专属代码不进入前端 |
| 依赖组合 | 精确可验证的默认组合、兼容矩阵、升级门禁和第三方许可清单 |
| 测试支持 | 单元、公共契约、真实运行时、网络集成、浏览器产物、资源和故障回归 |
| 文档 | 快速开始、配置／接口参考、插件教程、部署、排错、升级和已知限制 |
| 版本治理 | 框架／插件／接口／数据格式分别版本化；弃用、破坏性变更和迁移责任明确 |
| 部署 | 静态资源部署、服务端配置、同源／分离部署、反向代理、健康检查及退出约定 |

开发热更新和生产插件替换分别设计；开发重载不能被宣传成生产无损热升级。默认实现发生实质变化时，要求契约及真实集成回归，而非只更新版本号。

## 5. 插件组合与不变式

1. 核心不导入具体业务插件、素材格式或默认产品界面；依赖通过公开契约声明。
2. 服务绑定、界面覆盖、路由冲突和命令冲突各有明确规则，不能统一交给加载顺序决定。
3. 插件是能力与生命周期边界，不是每个按钮、函数都单独成包；完整职责优先于包数量。
4. 默认实现与替代实现遵循相同公开契约；替代时不要求消费者导入提供者私有文件。
5. 注册的路由、菜单、监听、订阅和任务均有归属与退出规则；停用插件不自动删除业务数据。
6. 应用实例、插件作用域、请求上下文、用户会话与任务实例分别拥有状态，禁止混为全局上下文。
7. 等待结束不等于就绪；超时不等于取消成功；清理返回不等于清理无错；请求成功不等于异步任务成功。
8. “可替换”不等于“任意时刻可热替换”；数据库、身份、任务等可能要求停止接单、收尾或重启。
9. 基础服务没有未说明的静默回退；兼容路径必须显式、可观察、有测试和退出条件。
10. 内核只保留必要引导机制，功能尽量可装配；不为了口号把建立插件容器本身也做成无限递归插件。

## 6. 启动、业务与退出流程

### 6.1 启动

输入：宿主类型、可信插件目录、装配文档、环境与配置来源。

流程：配置解析与校验 → 插件／版本／宿主要求预检 → 显式能力绑定 → 创建独立运行实例 → 依赖就绪后激活 → 审计必需能力 → 接收请求或呈现可操作界面。

输出：可控制的应用实例、公开服务、只读状态与诊断。必需能力未就绪时不能对外报告应用可用；失败关闭本轮已建立资源，不伪造成功。

### 6.2 三轮任务示例

示例只用于检验框架协作，不预先指定首个验收产品。

- 第 1 轮：前端提交输入 A 的引用、参数及修订，服务端校验身份／参数后创建任务 T1，返回任务标识；任务状态为排队、运行，日志关联请求与任务。
- 第 2 轮：用户改成输入 B，业务决定是否取消 T1 或仅令其结果失效。T1 即使随后完成，也不能覆盖 B；未接纳结果按资源规则处理。关闭页面释放订阅，不默认取消后台共享任务。
- 第 3 轮：任务 T2 成功，业务服务验证输入仍有效后提交结果；前端显示实际结果。重新打开时只能从明确的持久化来源恢复，内存任务不承诺崩溃恢复。

框架提供执行、通信和资源机制；业务负责结果有效性、提交条件与幂等语义。

### 6.3 退出

服务端停止接收新业务 → 按明确策略取消或排空任务／请求 → 依赖顺序清理 → 关闭连接及宿主资源 → 返回退出状态与异常。浏览器退出释放本实例视图和资源；不能依赖页面关闭事件完成关键持久写入。

清理超时需要表达“仍未释放／已隔离／后续如何处置”，不得把超时实例重新视为干净可复用。协议和状态机须先确认再实现。

## 7. 阶段计划与退出标准

W0—W3 已完成；W4—W6 尚未实现。选定范围统一接入当前执行指针，不自动创建全部空包或一次安装完整能力地图。

| 阶段 | 前置条件 | 主要产物 | 可观察退出标准 |
| --- | --- | --- | --- |
| W0 定位与边界 | 整体规划评审 | 范围、术语、模块边界、信任模型、仓库／命名决定、第一版验收组合 | 已决／未决明确；每项能力有所有者；不以功能清单代替接口与失败约定 |
| W1 核心收口 | W0 及现有代码复用审查 | 公共契约、装配、配置、生命周期、日志基础、诊断与清理策略 | 无界面独立启动；错误装配零激活；等待／失败／清理异常准确；双实例与重复启停可测 |
| W2 两种宿主 | W1 稳定边界 | 浏览器及服务端宿主、各自最小能力组合 | 纯前端独立构建部署；服务端不带 Vue／DOM；环境不兼容显式拒绝；两端均受控退出 |
| W3 最小全栈闭环 | W2 与通信／身份／数据边界决定 | 一个真实页面、一条业务接口、一种数据保存、关联日志与错误路径 | 请求贯通、非法输入和无权操作拒绝、实际保存回读、前后端版本不符可解释、无密钥泄漏 |
| W4 可替换界面与公共能力 | 相关公开契约已定义 | 界面组合、路由／命令／主题及第二实现；按需求补任务或实时能力 | 不改核心和业务即可换兼容布局／提供者；贡献撤销无残留；冲突与失败诊断可复现 |
| W5 跨应用复用 | 前述链路已收口 | 第二个不同用途应用、公共契约套件及干净消费样例 | 两应用依赖同一框架产物；不复制内部代码、不跨读私有状态；第二应用不要求加入产品专属内核分支 |
| W6 可交付框架 | W5 及目标交付方式确定 | 包产物、模板、文档、兼容矩阵、版本／升级／部署说明与门禁 | 新目录从发布候选包启动；源码与产物行为对应；静态／服务端部署验收；发布与安装状态分别记录 |

W2 的两个宿主可在契约稳定后分别验证；W4 的界面组合与 W3 的网络闭环是不同验收维度。任务持久化、实时恢复等没有代表需求时可不进入第一版，不能因此省掉核心错误、资源和安全边界。

## 8. 第一版候选范围

候选范围供评审，不代表已确认的开发承诺：

- 一套公共核心、可信插件装配、确定的配置规则、基础日志、诊断与受控退出。
- 浏览器／服务端两个最小宿主，支持分别使用。
- Vue 呈现及最小路由／命令／界面扩展组合，默认布局可替换。
- 一套 HTTP 接入与通信约定，覆盖输入校验、身份／授权接点、错误与取消语义。
- 一种代表性持久化方案，证明真实写入、回读和迁移职责，不同时适配全部数据库。
- 一个全栈闭环和一个不同用途的最小消费应用，覆盖独立依赖与替换证明。
- 插件示例、契约测试、构建／部署约定与基础文档。

条件项：文件上传、后台任务、SSE／WebSocket、定时、缓存、完整登录界面、追踪平台导出等，按代表性验收应用决定。第一版不启用某项，不等于从总体能力地图中删掉；应明确未启用和后续触发条件。

## 10. 统一验收矩阵

| 目标 | 验收方式 |
| --- | --- |
| 通用而非业务底座 | 导入边界检查；不同用途应用不要求修改核心 |
| 可独立消费 | 在新目录从框架包产物运行，不链接私有源码、不依赖原仓开发后门 |
| 可替换 | 两种服务／布局实现经同一公开契约工作，消费者不变 |
| 生命周期准确 | 等待、异步激活、失败、重复启停、双实例、并发关闭和超时行为测试 |
| 资源受控 | 真实监听、订阅、定时器、连接、Worker 等按本轮涉及范围检查，不只验证计数器 |
| 请求与用户隔离 | 并发请求／用户上下文不串线，权限服务端复核 |
| 通信可靠 | 畸形输入、版本不符、断线、超时、取消及有副作用调用的重试限制 |
| 数据可信 | 真实保存回读，失败不假成功，迁移责任与取消后的提交边界明确 |
| 日志可用且有界 | 关联可追踪、敏感字段不输出、输出异常不破坏业务、不无限缓存 |
| 界面实际可用 | 生产产物的整体／局部截图、键盘、悬浮／禁用、刷新深链接与受限视口验收 |
| 配置与部署正确 | 配置来源可诊断、缺配置拒绝、前端无密钥、健康／就绪正确、优雅退出 |
| 升级可解释 | 契约兼容、弃用提示、已确认迁移及默认依赖组合回归，不静默回到旧实现 |

测试数量、目录数量或文件变短都不能单独证明框架成立。仅类型检查／HTTP 200／开发页通过，不代替实际构建与包消费验收。

## 12. 风险与控制

- 范围膨胀：能力地图与第一版范围分开，每阶段只兑现已批准的验收组合。
- 抽象过度：用第二个不同用途应用检验边界，不凭想象造万能模型和数十个空包。
- 平台泄漏：浏览器、服务端专属实现隔离，产物检查防止 Node 依赖或密钥进入前端。
- 库版本风险：Cordis 仍处于 API 不稳定期，保留精确基线、补丁守卫与契约回归；不因规划顺手升级。
- 安全误判：可信插件机制不宣称沙箱；运行隔离、用户权限、请求隔离分别验证。
- 状态混乱：运行、请求、会话、任务和业务修订各有唯一所有者，日志只观察不接管状态。
- 不可维护的自动装配：先显式配置；组合包须能解释最终插件和绑定，自动发现后续另行评估。
- 交付假完成：源码测试、生产构建、包消费、部署、发布和正式安装分别给证据。
